# U6.6 — per-app SELinux rules

Removes the per-app SELinux rule editor and the whole storage-plus-apply channel behind it. The
profile's SELinux **domain** stays; only the rules layered on top of it go. Maps to upstream
`U6.6 profile` (`profile.rs` 79 lines) and the rules half of the App Profile screen.

## Why

KernelSU lets a root app's profile name a SELinux domain and then attach arbitrary policy
statements to it. The statements never leave userspace: `uapi/app_profile.h` has
`selinux_domain` and no `rules` field, and `Natives.kt` carried the comment
`// this field is save in ksud!!`. The path was Manager writes `/data/adb/ksu/profile/selinux/<pkg>`
-> ksud reads the directory at boot -> `sepolicy::apply_file` -> `live_patch`.

That is a text box that lets anyone with the Manager grant themselves SELinux permission, applied
before the user has any way to review what the previous rules were still doing; the rules are
additive and only take effect on the next boot, and the editor's own hint said so in hard-coded
Chinese. The fork does not want a per-app policy editor. Removing it does not touch the two
escapes it looks similar to: a module's `sepolicy.rule` and the `ksud sepolicy` subcommand both
survive, and the profile's `selinux_domain` switch survives.

gone, and `checkSelinuxContext` validates in place as the field's `supportingText`. Read-only
callers render the same field non-editable instead of opening a sheet that repeats it.

Before the change the same command echoed the parsed `NormalPerm` and wrote
`/data/adb/ksu/profile/selinux/com.example.test`, so this is the behavioural difference rather
than only a compile. The App Profile and template screens were not opened: the editor is gone and
the compile is what covers the remaining screen code.

## Sync risk

Upstream can keep editing `profile.rs` and the App Profile screen. Three collision points:

1. `profile.rs` — upstream's `set_sepolicy` still writes the file and calls `apply_file`. A sync
   that brings the body back would silently restore the channel, because the no-op looks like a
   normal function. G1 greps for the stub body, not the name.
2. `TemplateInfo.kt` — upstream may add a field next to `context`; the `rules` parameter was
   removed from the constructor, so a re-add is a compile error rather than a silent loss. That is
   the intended tripwire.
3. `Natives.Profile` — the `rules` property is gone. Upstream's JNI never marshalled it, so a
   re-add on the Kotlin side alone would look correct and do nothing.

Old rule files under `/data/adb/ksu/profile/selinux/` are left in place and read by nobody. A user
who wants their rules back has to move them into a module's `sepolicy.rule`.

## Rollback

Revert this commit. The parsed rules were never persisted anywhere except that directory, so
reverting restores the reader and the files it was reading are still there. No ABI number was
retired, no feature id was reused, and no data was migrated, so nothing has to be undone on a
device beyond a reboot.
