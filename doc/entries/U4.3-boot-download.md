# U4.3 — remote boot image download

Removes the install method that fetched a full OTA or factory image over HTTP, extracted the boot
partition from it, and patched that. Local `boot.img` selection and direct install to a slot stay.
Maps to upstream `U4.3`-adjacent Manager code: `InstallMethod.DownloadFile`,
`downloadBoot()`, `probeRemoteBootPartitions()` and the `core/` helpers behind them.

## Why

The Manager offered "Download a file and patch": paste a URL, and the app would range-request an
OTA payload, pull the `boot`/`init_boot`/`vendor_boot` partition out of it, and hand the result to
`ksud boot-patch`. It needed four supporting classes — `DataSourceChannel` (an OkHttp-backed
`SeekableByteChannel`), `Payload` (update-engine payload parsing over that channel),
`ExtractImage` (partition extraction and magic sniffing) and `BootKernelVersion` (KMI scanning) —
none of which anything else used.

The fork does not need it. Patching a correct boot image depends on the exact device and ROM the
user is running, and downloading an arbitrary URL is a weaker starting point than picking the
image already on the device. Direct install already covers the OTA case for a rooted AVD-class
device. Removing it also drops the only place in the Manager that accepted a user-supplied URL and
fetched it with no origin constraints.

**The protobuf toolchain goes with it.** `Payload.kt` parsed the update-engine payload with the
generated messages from `app/src/main/proto/update_metadata.proto` — 454 lines of upstream AOSP
proto2, the only `.proto` in the project. That made the Manager carry the `com.google.protobuf`
Gradle plugin, a `protoc` artifact download in every build, and `protobuf-kotlin-lite` at runtime,
for one class that one install option used. All three go with the feature. This is the part that is
easy to miss: deleting `core/` leaves the build green, because the generated messages are produced
from a `.proto` nobody references any more rather than from a missing import.

This is **not** an empty implementation, unlike the `ksud profile set-sepolicy` stub in
[U6.6](U6.6-profile-selinux-rules.md). The download method is a radio button in the install
picker: a stub would leave the user choosing an option that silently does nothing, which is worse
than the option not existing. The UI goes, and so does the data model behind it.

`ksud boot-patch` is untouched: the command-line path never depended on any of this.

## Sync risk

Upstream still owns all of this code, so a sync can put it back. Two shapes:

1. **Partial restore.** Upstream touching `KsuCli.kt` near `installBoot` would apply cleanly and
   leave no `downloadBoot`; upstream adding a call to it is a compile error, which is the
   tripwire working. The dangerous case is a clean apply that restores `core/` alone — nothing
   references it then, and the build stays green with dead code back in the tree. G1 greps for the
   directory, not for a caller.
2. **InstallMethod.** Removing the `DownloadFile` branch made the `when` in `InstallEntry`
   exhaustive over three variants. Upstream re-adding a fourth breaks that `when` at compile time,
   which is correct: somebody has to decide whether the fork wants it.
3. **protobuf silently stays gone.** Upstream adding a protobuf-based feature post-dates this
   removal; a sync would then fail to resolve `libs.plugins.protobuf`, which is a loud failure and
   the right one. The silent case is the reverse: a sync restoring `Payload.kt` alone leaves it no
   longer compiling, so it cannot rot back in unnoticed.

## Rollback

Revert this commit; `core/` and the string keys come back with it. Nothing was persisted on a
device, no in-flight download format changed, and no ABI number was retired. A user who wants the
same effect without the feature can patch a boot image they already have, or use
`ksud boot-patch` directly.
