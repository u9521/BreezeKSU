# Manager UI

Covers: manager/app/src/main/java/me/weishu/kernelsu/ui/, manager/app/src/screenshotTest/

## One renderer, one shell

No `UiMode` enum. A second skin means replacing `ui/BreezeShell.kt` — theme, blur flag and shared overlay window — while the navigator, pager and every `NavEntry` view model store above it stay put. A skin is a composition, not a branch in every screen.

`MainActivity` renders `ui/BreezeApp.kt` and `WebUIActivity` renders `BreezeWebUIRoot`, both unconditionally and both through `BreezeShell`, so the two windows cannot drift. `MainActivity` declares no `configChanges`: rotation recreates it, so what must survive lives in a ViewModel or `rememberSaveable`.

## Five layers, one direction

`verify-arch-layers.mjs` enforces the graph with zero exemptions.

| Layer | Path | May import |
| :--- | :--- | :--- |
| 1 | `data/`, `core/`, `magica/`, `profile/`, `KernelSUApplication.kt`, `Natives.kt`, `Kernels.kt` | no `ui/`, no Compose |
| 2 | `ui/theme/`, `ui/icons/`, `ui/util/` | layer 1, own group |
| 3 | `ui/component/common/`, `ui/component/breeze/` | layers 1–2; `common/` never `breeze/` |
| 4 | `ui/nav/`, `ui/animation/` | layers 1–3 |
| 5 | `ui/screen/<feature>/`, `ui/webui/` | layers 1–4; hosts never import each other |
| root | `ui/BreezeApp.kt`, `ui/BreezeShell.kt`, `ui/MainActivity.kt` | everything |

Three rules ride along: a component file must sit under `ui/component/common/` or `ui/component/breeze/`; Layer 3 never reaches `Natives`, `Kernels`, `KernelSUApplication` or `ksuApp`; and a file under `ui/viewmodel/` fails outright — F5 dissolved that package into the pages it serves.

Layer 4 must not import `ui/screen`, `ui/webui` or the composition root: route keys and transitions are what screens plug into. `BreezeIntentRouter` therefore reports a zip via `onRequestInstallModule` and a WebUI link via `onOpenWebUI`; the root owns the dialog and the activity. A new main tab edits `BreezeRoute.TabRoute` alone — order, label and icon derive from the enum, so the pager, bar and rail cannot drift.

## A screen is three files

`ui/screen/<feature>/` is a funnel and the compiler enforces the rungs: `*ViewModel.kt`/`*UiState.kt` hold and derive state, `*Entry.kt` binds it, `*Breeze.kt` draws it. The first two take zero `ui.component.*` and zero `material3.*` imports; a `SnackbarHostState` or `rememberConfirmDialog` handle in an `*Entry.kt` is the smell that the page leaked upward. `*Entry.kt` owns `viewModel()`, platform capabilities, navigation callbacks and `pop()` on a bad argument; `*Breeze.kt` gets `(state, actions)` and nothing else.

Removing a ViewModel without its `*Breeze.kt`/`*Entry.kt` pair leaves dead references that still look generated; list both paths in the pruning entry's residue checklist first.

## Page skeleton

`BreezeScaffold` plus `BreezeTopAppBar` is the skeleton; a page supplies `topBar` and content.

- It unions `LocalNavigationBottomInset` into `contentWindowInsets`, applies `nestedScroll(scrollBehavior.nestedScrollConnection)` and `nestedScroll(searchBarScrollBehavior.nestedScrollConnection)` itself, and hangs `hazeSource` on the content box only while `LocalEnableBlur` holds. A page therefore adds none of the three: no `bottomInnerPadding`, no second `nestedScroll`, no blur source of its own — and blur-off costs no recording. `searchBarScrollBehavior` keeps `initialScrollOffsetLimit = 0f`: the `-Float.MAX_VALUE` default lets a search bar consume pre-scroll on pages without one.
- `message: UiMessage?` becomes a snackbar and calls back with `onMessageShown(id)`. One-shot feedback travels as `UiMessage`, never a direct `showSnackbar` in an `*Entry.kt`.

Scrolling content goes through `BreezeScrollColumn(innerPadding, showScrollbar = …)`: it applies the horizontal insets and reserves the top and bottom ones as spacers, so content scrolls under the bars while the first and last items stay reachable; the bottom spacer cancels the arrangement gap, so `spacedBy` cannot inflate it. Do not hand-write `onlyHorizontal()` plus two `Spacer`s, nor put a `navigationBarsPadding()` item in an already-inset list.

## Icons, modals, previews

Every icon is an `ImageVector` from `ui/icons/`, generated by `fetch_material_icons.py` from `.agents/skills/material-symbols-icons/icons.toml`. `material-icons-extended` is not a dependency; add the name to the manifest and regenerate instead.

Dialogs and sheets build on `BreezeOverlay`: [overlay](overlay.md) for window invariants and blur, [overlay stack](overlay-stack.md) for layers and animation. Previews live in `manager/app/src/screenshotTest/` and reach no APK; a broken one fails the screenshot-test compile, not the app build.
